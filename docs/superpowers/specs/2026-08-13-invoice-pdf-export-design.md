# Invoice PDF export

**Status:** approved 2026-08-13

## Context

The invoice exists on screen and in the database. It cannot yet leave the app as
a file, which is the last thing the Google Sheet still does better — its Apps
Script exports a PDF to Drive.

The original plan named the sheet's exported PDF as the visual target for this
phase. It never arrived, so the on-screen invoice was built from the sheet's
*data* instead, and has been reviewed for weeks. **That on-screen document is
now the target**, decided 2026-08-13. The old template's quirks — reserved blank
rows, a printed "TAX 0%" on every invoice, a floating totals block — were
deliberately dropped when `InvoiceDocument.tsx` was written and are not coming
back.

Emailing the invoice is Phase 5 and is what actually retires the spreadsheet.
It is out of scope here, but it is the reason for the main architectural choice
below.

## Decisions

| Question | Decision |
|---|---|
| Renderer | `@react-pdf/renderer`, via CrewTracker's `PdfParts` injection |
| Visual target | `components/InvoiceDocument.tsx`, section for section |
| Typography | Oswald vendored for headings; built-in Helvetica for body |
| Money | Printed from stored cents. Never recomputed. |
| Scope | Builder + browser download. No email route. |

### Why `@react-pdf/renderer` and not print CSS

A print stylesheet on the existing page would be near-free and pixel-perfect —
`InvoiceDocument` is already a white paper document, and Oswald and Inter would
come along at no cost. It was rejected on one point: it cannot produce a file on
the server, so Phase 5 would need a second, independent PDF implementation, and
the file a client receives would be generated by different code than the file
that was approved. Headless Chrome can do both but is heavy and slow to
cold-start on Vercel for a one-page document.

The cost of this decision is real and should be stated: the layout is
re-expressed in `@react-pdf`'s primitives rather than reusing the React
component, so **two layouts must be kept in step by hand.** Mitigations are the
shared input type below, identical section ordering, and cross-references in
both files' comments.

## Architecture

### `lib/invoicePdf.tsx`

Builds the document and imports nothing heavy — no `@react-pdf/renderer`. The
caller injects the primitives:

```ts
export type PdfParts = {
  Document: any; Page: any; Text: any; View: any; Image: any; StyleSheet: any
}

export function buildInvoicePdf(parts: PdfParts, data: DocumentData)
```

`DocumentData` is **imported from `components/InvoiceDocument.tsx`, not
redeclared.** One type describes what an invoice document needs; the screen and
the PDF are two renderers of it. If the on-screen document gains a field, this
module fails to compile rather than quietly omitting it.

**Font registration is the caller's job, not the builder's.** The builder only
names `fontFamily: 'Oswald'`. The browser registers it from a URL; the Phase 5
server will register the same file from disk. A builder that registered fonts
itself would have to know which environment it was in — the exact coupling
`PdfParts` exists to prevent.

### `components/DownloadInvoiceButton.tsx`

`'use client'`. Dynamically imports `@react-pdf/renderer` on click — it is
roughly 2MB and must not enter the main bundle — registers Oswald, calls
`pdf(doc).toBlob()`, and triggers a download named
`Invoice-389-Journey-Church.pdf` (client name sanitised to filename-safe
characters; falls back to `Invoice-389.pdf` when there is no client).

While generating, the button reads "Preparing…" and is disabled. A failure
renders an inline error rather than an alert, matching every other action in
this app.

### Fonts

`public/fonts/Oswald-Bold.ttf`, vendored. Weight 700, because that is the only
weight `InvoiceDocument` renders Oswald at, and it does so in exactly two
places: the "The Audio Smith" wordmark and the "Total due" label. Static TTF,
not the variable font, which `@react-pdf` does not handle.

Everything else on the page — including the uppercase `[11px]` section labels,
which are Inter semibold and **not** Oswald — falls to Helvetica, built into the
PDF format. At 9–10pt on paper it is close enough to Inter that the difference
is not worth ~1MB of vendored files. CrewTracker's PDF registers no fonts at
all; this adds one, for the two elements that actually read as the brand.

## Layout

Letter, 40pt margins. A direct translation of `InvoiceDocument.tsx` in the same
order:

1. Amber rule across the top — the way the site closes its header
2. Logo (`public/logo.png`, 512×512, drawn at 44pt) + "The Audio Smith"
   wordmark with an amber "Smith" + legal name; business address block right
3. Bill to (snapshot, falling back to the client's name and address) and the
   invoice meta block — number, date, terms, due
4. Line table: Description / Qty / Price / Total
5. Totals: subtotal, tax if non-zero, deposit if non-zero, total due
6. Footer: remit-to and notes, each only when present

**Colours are hardcoded, not tokenised:** `#ffffff` paper, `#121212` ink,
`#cbd5e1` rules, `#f59e0b` amber, and `#737373` / `#525252` for the two muted
greys (Tailwind `neutral-500` / `neutral-600`, which `InvoiceDocument` uses
deliberately). Same reasoning as on screen — a document a client receives does
not follow anybody's colour scheme.

### Pagination

Real data does not need it: the longest of 105 invoices has 11 lines, the
average is 3.2, and none exceeds 12. It is a few lines of code, so:

- the table header row repeats on every page
- the totals block is marked unbreakable so it cannot split
- a page number prints only when the document runs to more than one page

## Correctness

**The PDF prints stored cents. It never recomputes them.** `line_total_cents`,
`subtotal_cents`, `tax_cents`, `deposit_cents` and `total_cents` are rendered
through the existing `formatUSD`; quantities through `formatQty`. Recomputing in
a second place is how a PDF comes to disagree with the record it represents —
and the imported history contains both $106.36 and $106.37 for the same computed
rate, so re-deriving would rewrite invoices already sent.

Dates render through `lib/dates.ts` `formatDateLong`. Never `new Date()`: a
plain date pushed through local time prints a day early west of UTC, which has
already happened once in this app.

Two invariants carried from the screen:

- Zero-value tax and deposit rows are omitted.
- **ACH bank details are never rendered.** `settings.ach_details` is not part of
  `DocumentData`, is not passed in, and must never be added. `remit_to` prints;
  clients who want ACH ask for it. Bank numbers on a forwarded PDF are an
  unnecessary exposure.

## Testing

The injection makes this testable without running a PDF engine. Pass stub
`parts` that record the tree, and assert against it:

- Every money string in the tree equals `formatUSD` of the corresponding stored
  cents — nothing is recomputed or rounded a second time.
- An invoice with zero tax and zero deposit produces neither row; one with a
  deposit produces it, negated.
- ACH details cannot reach the document. `DocumentData['settings']` has no
  `ach_details` field, so the test passes a settings object with one attached
  (cast past the type, the way a careless future change would) and asserts no
  string in the tree contains it. The type is the real guard; this catches
  somebody widening it.
- A multi-line invoice emits one row per line, in `position` order.

Then generate a real PDF from an actual invoice and read it back, against the
on-screen version side by side. The tests prove the data is right; only looking
at it proves the layout is.

## Out of scope

- The email attachment route. Phase 5 — it needs the Resend sending subdomain
  and DNS records first.
- A hosted invoice page for clients. Undecided, and unrelated.
- Batch export of several invoices at once. No demand for it.
- Vendoring Inter. Rejected above.
